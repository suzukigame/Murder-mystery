# Steam 展開拡張プランと実現性再評価

本ドキュメントでは、現在の Murder-mystery プロジェクト（React + Node.js + Socket.io）を Steam 向け PC デスクトップアプリとして展開するまでのロードマップ、具体的なタスク、および実現性について再検討した結果をまとめます。

---

## 1. 実現性の再評価 (Feasibility)

**総合実現性: 高い (ただし、バックエンド運用方針により難易度が変動)**

現在のプロジェクトは Web 技術（React + Node.js）で構築されているため、フロントエンドのデスクトップアプリ化自体は非常に簡単です。最大の障壁は「マルチプレイ用サーバーのホスティング費用と管理」および「Steamworks APIとの連携」になります。

| 領域                   | 難易度 | 分析とアプローチ                                                                                                                                                                                           |
| :--------------------- | :----- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **アプリ化（ガワ）**   | **低** | **Tauri** (Rustベース) または **Electron** を使用。現在のコード資産を100%流用しつつ、デスクトップアプリとしてパッケージング可能です。実行速度やバイナリサイズの観点から **Tauri** を強く推奨します。       |
| **バックエンド運用**   | **中** | Steamユーザー同士がマッチングするためには、中央集権型の 専用ゲームサーバー（VPS, AWS, Render等）を常時稼働させる必要があります。ランニングコストが発生するため、収益モデル（有料販売等）の検討が必要です。 |
| **ロビー・マッチング** | **中** | 現状の「ルームID」システムを拡張し、「公開ルームリスト（サーバーブラウザ）」や「プライベートルーム（パスワード）」の堅牢な実装が必須となります。                                                           |
| **Steam 連携**         | **中** | `steamworks.js` や Tauri の Steam プラグインを用いることで、Steamの認証情報（ユーザー名やアイコン）の取得や、フレンド招待機能（Rich Presence）の実装が可能です。                                           |

---

## 2. 推奨される開発アプローチ（ハイブリッド方式）

完全にゲームが完成してからSteam化に着手するのではなく、**「ブラウザ環境でゲーム自体の完成度を高めつつ、中盤で一度だけデスクトップ化のテストを挟む」** アプローチを強く推奨します。

### 開発進行の推奨ステップ
1. **ブラウザ環境でのクオリティアップ（現在）**: BGM追加、イラスト挿入、UI/UXの改善など、ゲームの根幹部分の開発は、修正と確認のサイクルが圧倒的に速い現在のブラウザ環境（React開発サーバー）で行います。
2. **デスクトップ化の早期検証（中間テスト）**: ゲームのアルファ版ができた段階で、Tauri等を用いて「PCアプリのウィンドウ内で正常に動くか」「BGMの自動再生ブロック等に引っかからないか」だけをテストします（Steam API等はまだ入れません）。
3. **完成度のさらなる向上**: アプリ版での動作リスクが払拭されたら、引き続きコンテンツ追加やロビー機能の強化を進めます。
4. **最終結合とSteam展開**: ゲームが完成し、クラウドサーバーの運用目処が立った最終段階で、Steamworksの連携（自動ログインやフレンド機能）を行い、ストアへの登録とテストを開始します。

---

## 3. デプロイメントプラン (Phases)

段階的にリリースへ向けて開発を進めるための4フェーズプラン（上記アプローチの具体的な実装手順）です。

### Phase 1: デスクトップアプリ化検証 (Tauri導入)
目的：ローカル環境でReactアプリをデスクトップアプリとして動かす。
- バックエンドはローカル(`localhost:3001`)を向かせた状態で、デスクトップ上での動作感（フルスクリーン対応、キーボード操作など）を検証・最適化します。

### Phase 2: クラウドサーバー構築とルーム機能の完成
目的：誰でもインターネット越しに安定して遊べる基盤を作る。
- Node.js カスタムサーバーを Render.com などのクラウド環境にデプロイし、本番用のURL（wss://...）へ接続できるようにします。
- 動的に部屋を作成・解散できる「部屋割り・ロビーシステム」を完成させます。

### Phase 3: Steamworks API 統合
目的：SteamプラットフォームならではのUXを提供する。
- Steam SDK を組み込みます。ユーザーがゲームを起動した際、名前入力画面をスキップして **Steam名** を自動取得する仕組みなどを導入します。
- Steam オーバーレイを介した「フレンドをゲームに招待する」機能を実装します。

### Phase 4: ストア登録とクローズドテスト
目的：リリース準備。
- Steam Direct への登録（登録料 $100）、ストアページの作成、カプセル画像（バナー等）の準備。
- Steam のベータブランチ機能を利用し、開発者やフレンド間でのクローズドなプレイテストを実施してバグを潰します。

## 4. 具体的なタスクリスト (Tasks)

今後の機能開発の参考となるチケット・タスクの粒度です。

### [App] フロントエンド (Tauri化 & UI拡張)
- [ ] **Tauri プロジェクト初期化**: 既存の React プロジェクトをラップする Tauri のビルド設定 (`tauri.conf.json`) を追加。
- [ ] **ウィンドウ制御**: 「フルスクリーン切替」「ウィンドウのリサイズ制御（極端に小さくできないようにする制限）」の実装。
- [ ] **キーボード対応**: Enterキーでのチャット送信、Escキーでの設定・終了メニュー表示の実装。
- [ ] **音量・設定機能**: BGM/SE の音量をOSのミキサーとは別にゲーム内で制御できるオプション画面の作成。

### [Server] バックエンド (クラウド環境 & ロビー)
- [ ] **クラウドデプロイ**: `render.yaml` や Dockerfile の最適化とホスティング環境での稼働テスト。
- [ ] **ロビー管理の高度化**: 部屋が空になったら自動でメモリから削除するガベージコレクション機能の実装。
- [ ] **ルーム一覧表示 (サーバーブラウザ)**: ゲーム起動直後に「現在ホストされている公開ルームの一覧と人数」を取得して表示する API エンドポイントの作成。
- [ ] **サーバーコスト最適化**: 1部屋あたりのメモリ消費量チェックと、定期的な再起動スクリプトの用意。

### [Steam] Steamworks 連携
- [ ] **Steam SDK の統合**: `steamworks.js` パッケージの導入。
- [ ] **自動認証**: ログイン画面を改修し、Steam環境で起動された場合は Steam ID と名前をデフォルトで利用する。
- [ ] **Rich Presence**: 「現在ロビーで待機中」「セッション中 (Turn 3/8)」といった状態を Steam のフレンドリストに表示する。
- [ ] **(オプション) 実績実装**: 「ハッカーで社員全員を騙して勝利した」「DevOpsで3つのBOTをすべて生存させた」などの Steam 実績(Achievements)の発火処理。

---

## 5. 今後のアクションに向けて

現在のアーキテクチャは十分に Steam 展開に耐えうる作りになっています。
デスクトップアプリ化のガワを作る前に、**ブラウザ環境でそのまま検証でき、かつ将来の展開に直結する「BGM・イラストの追加」や「ルーム管理システムの高度化（ルーム一覧表示）」** を進めるのが、最も効率的な次の一歩となります。
