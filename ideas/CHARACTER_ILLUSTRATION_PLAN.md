# キャラクターイラストと「着せ替え」機能の技術分析

本ドキュメントでは、現在のアスキーアートやシンプルなターミナルUIベースの画面に、本格的な「キャラクターイラスト」および「着せ替え（スキン・カスタマイズ）」機能を導入するためのアプローチと、Steam展開を見据えた技術難易度を検討します。

---

## 1. 総合評価

**実現性: 非常に高い (フロントエンド改修がメイン)**
**技術難易度: 4/10 (Steam想定でもWeb技術で完結可能)**

現在の React 環境では、画像の重ね合わせ（レイヤー処理）や動的なアセット読み込みは非常に得意です。バックエンドのデータ構造を少し拡張するだけで、「プレイヤーがどのスキンを選んでいるか」を全員に同期させることができます。

---

## 2. アプローチ別 実装方法と難易度

着せ替え機能の実装には、大きく分けて2つのアプローチがあります。

### アプローチA： 一枚絵（スキン）切り替え 방식
あらかじめ完成した全身イラスト（例：「デフォルト」「スーツ姿」「サイバーパンク風」など）を用意し、プレイヤーが選択したスキンのIDに基づき1枚の画像を切り替える方式です。

- **難易度**: **低 (2/10)**
- **実装方法**:
  - 画像として `charA_skin1.png`, `charA_skin2.png` を用意する。
  - フロントエンドで `<img src={selectedSkinPath} />` として描画するだけ。
- **メリット**: イラストレーターの負担が少なく（完成品を描けばよい）、描画のズレや不具合が起きない。
- **デメリット**: 組み合わせの自由度がない（帽子だけ変える、といったことができない）。

### アプローチB： レイヤー（パーツ）合成方式 (ペーパー・ドール式)
キャラクターの「素体（ベース）」「目」「髪型」「服」「アクセサリー」などをすべて透過PNGとして個別に用意し、React上で位置を合わせて重ねて表示する方式です。

- **難易度**: **中 (5/10)**
- **実装方法**:
  - `z-index` または HTML5 Canvas を使用して、複数枚の透過PNGを重ね合わせる。
  ```jsx
  <div className="avatar-container">
    <img src="/assets/base.png" className="layer-base" />
    <img src="/assets/clothes_03.png" className="layer-clothes" />
    <img src="/assets/hat_01.png" className="layer-accessory" />
  </div>
  ```
- **メリット**: 非常に高い自由度。「ガチャ」や「課金アイテム」「Steam実績報酬」として個々のパーツを配布・販売しやすい。（Steamエコノミーとの相性抜群）
- **デメリット**: アセットの準備（ピクセル単位での位置合わせ機能など）に大きな手間がかかる。

## 3. Steam 展開を見据えたメリットと懸念

着せ替え機能を実装することは、Steam展開において**「マネタイズ（収益化）」と「プレイヤーのモチベーションアップ」に直結**するため、極めて戦略的価値が高いです。

### メリット (Steamエコノミーとの親和性)
1. **Steam インベントリ連携**: Steamworks API の「Steam Inventory Service」を利用すれば、帽子や服のパーツを「Steamアイテム」として管理できます。プレイヤー同士でトレードさせたり、Steamコミュニティマーケットで売買（手数料収入）させることも可能です。
2. **実績報酬**: 「ハッカーで3回勝利した」という Steam 実績(Achievement) の解除と同時に、限定のハッカー風スキンをアカウントに付与できます。
3. **DLC販売**: アプリ自体を無料でリリースし、「プレミアムスキンパック」をDLCとして販売するモデル（F2P + コスメティック課金）が構築やすくなります。

### 懸念事項 (アセット管理と通信量)
- **バイナリサイズ**: パーツ画像が増えると、ゲーム自体のファイルサイズが肥大化します。Webブラウザ版では「初回ローディングの遅延」に繋がりますが、Steam（デスクトップアプリ版）であれば事前にギガバイト単位でダウンロードさせられるため、**Steam展開であればむしろこのデメリットは解消されます**。

## 5. シークレットキャラクターと実績解放システム

キャラクター選択画面において、特定の条件を満たすまで一部のアバターを「シークレット（シルエット状態）」として隠し、実績解除に合わせて解放する仕組みを導入します。

### 5.1 コンセプト設計
- **初期表示**: `AVAILABLE_SKINS` のうち、初期キャラ以外は名前が「???」となり、画像はCSSフィルタ等でシルエット（黒塗り）として表示される。
- **ロック状態**: 未解放のキャラクターを選択しようとすると、「解放条件（例: ハッカーで1勝する）」がツールチップなどで表示され、選択できない。
- **データ保存**: プレイヤーの解放進捗は当面ブラウザの `LocalStorage` を用いて保存し、のちにSteam Cloudへ移行する。

### 5.2 実装までのタスク一覧

1. **[データ・ロジック層] 解放条件システムの構築**
   - [ ] `skins.ts` の `ISkinData` に `isSecret: boolean` および `unlockCondition: string` などを追加。
   - [ ] 解放済みスキンIDの配列を `LocalStorage` に保存・読み込みするユーティリティ関数（`useAchievements` フックなど）を作成。

2. **[サーバー層] 実績判定機能の追加**
   - [ ] `server.ts` のゲーム終了時（リザルト処理時）に、各プレイヤーがどの実績条件（ハッカー勝利等）を満たしたかの判定ロジックを作成。
   - [ ] 達成した実績データをクライアントへ送信するイベント（`achievement_unlocked`）を実装。

3. **[クライアントUI層] キャラクター選択画面の改修**
   - [ ] `SkinSelectorModal.tsx` を修正し、未解放キャラは `filter: brightness(0)` などでシルエット化し、名前を伏せる。
   - [ ] 未解放キャラをクリックした際に、解放条件を表示するUI（鍵アイコンやポップアップ）を作成。

4. **[クライアントUI層] 実績解除時の演出**
   - [ ] ロビーまたはリザルト画面で、新しいキャラクターが解放されたことを知らせる演出（トースト通知など）を実装。
